Interactor agrega un módulo/tool; no lo registres como Agent. El código fuente fechado y las ejecuciones congeladas siguen siendo cosas distintas.

- **Editor:** `agent_page_editing.js` es el dueño del documento de CodeMirror, la línea base de cambios, la codificación y el snapshot de guardado. `agent_page_canvas.js` es dueño de la generación y la cancelación de carga/refresh. La Vista previa y el Source de Markdown comparten el buffer; HTML/SVG quedan como source inerte; al guardar un PDF se copia el PDF original. Nunca leas un elemento de compatibilidad oculto en vez del editor.
- **Archivos nativos:** `canvas_file_views.py` y `native_dialogs.py` dan Guardar como/lectura/guardado locales. La autenticación, el CSRF, el acceso al host sólo por loopback, las capacidades ligadas a la cuenta/sesión y las verificaciones completas de revisión evitan que un nombre de browser se convierta en un path de host arbitrario. El reemplazo existente de Windows conserva los metadatos; la mecánica de backup/restauración de la DB no cambia.
- **Interactor:** `agent/interactor/` conecta el loop síncrono de tools con el browser a través de `ws/interactor/` autenticado por sesión. La identidad de pestaña que emite el servidor viaja por ContextVar; los comandos acotados y los recibos verifican el documento/revisión y el buffer completo. Los mensajes del browser confirman/acceden/detienen; no pueden pedir comandos con un host-path arbitrario.
- **Tutor:** lee el texto sin guardar recién tomado, escribe un segmento pequeño, guía el siguiente campo y termina las mutaciones del turno. Continuar inicia un chat/lectura nuevos. Las opciones preparadas coinciden localmente, sin una llamada al modelo por cada tecla. El input del usuario y Detener ganan; las pestañas ocultas se pausan con recuperación acotada en vez de repetir ediciones.

El bundle del editor offline, los archivos del browser de Interactor, los imports congelados y los inventarios de source/static tienen que viajar juntos.
- **Intención:** escribir una contraseña no es ser dueño de cada comando; un campo de email de un wizard o una respuesta DONE no son consentimiento de notificaciones. Conserva los tutoriales genuinos que ejecuta el usuario. El wizard del catálogo usa createsuperuser y por eso crea una cuenta administrativa.

Este archivo es la **fuente autoritativa de las descripciones legibles para personas** de cada workflow agent que se muestra en la barra lateral del Agentic Control Panel de Tlamatini.

La vista de Django `agent.views.agentic_control_panel` parsea las filas de tabla bajo `## Workflow Agents` de abajo e inyecta la columna `Description` en la página como el JSON `agent_purpose_map`. El frontend (`acp-canvas-core.js`) lee ese JSON y usa el texto como el **tooltip al pasar el cursor** sobre cada agent de la barra lateral y como el cuerpo del diálogo **Descripción** cuando el usuario hace clic derecho sobre un agent en el canvas.

Editar aquí la celda `Description` de una fila cambia dos cosas:
- the documentation read by humans, AND
- el texto de la interfaz en vivo que se muestra a los usuarios finales.

La búsqueda no distingue mayúsculas ni puntuación: la llave de cada fila es `re.sub(r'[^a-z0-9]+', '', name.lower())`. Así que "Kyber-KeyGen", "Kyber KeyGen" y "kyberkeygen" resuelven todas a la misma descripción.

Las descripciones están escritas para **lectores no expertos** — ante la duda, prefiere la redacción más larga y amable en vez de una línea escueta. Alguien que nunca ha visto el agent debería poder entender **qué hace, cuándo usarlo y cuáles son sus inputs/outputs principales** con una sola lectura del tooltip.

## Workflow Agents

> > **Nota — el lector de PDF del canvas no es un agent.** Abrir un PDF en el canvas del *chat* y convertirlo en contexto (2026-09-16) es una función de la página, no un workflow agent, así que no tiene fila en este archivo: ve [docs/pdf-canvas.md](docs/pdf-canvas.md). Sí reutiliza el agent **Image-Interpreter** de abajo para su análisis de imágenes opcional, y es distinto de **File-Extractor** (que extrae el texto crudo de un PDF que tú nombras) y de **PDFer** (que *crea* PDFs).

El diseñador visual de workflows trae **86 tipos de agent**, agrupados abajo según su rol en un flow. Arrastra cualquiera al canvas, conéctalos entre sí y presiona *Iniciar* — los agents corren como procesos separados que emiten logs y se comunican entre ellos a través de sus archivos `config.yaml`.

### Agents de control

Estos agents dan forma al ciclo de vida de un flow: cuándo empieza, cuándo termina y qué se limpia después.

| Agent | Descripción |
|-------|-------------|
| **Starter** | El punto de entrada de cada flow. Cuando el usuario hace clic en *Iniciar*, el Starter es el primer agent que corre; su único trabajo es lanzar los agents que están en su `target_agents`. Piénsalo como el botón verde de Play del canvas — no hace trabajo real por sí mismo, sólo arranca el chain. |
| **Ender** | Termina un flow de forma ordenada. Mata cada agent que está en su `target_agents`, luego lanza lo que esté conectado a su `output_agents` (normalmente un FlowBacker para los backups, seguido de Cleaners que borran los archivos transitorios). Usa Ender al final de cada flow que deba apagarse solo. |
| **Stopper** | Un agent quirúrgico para "matar al vecino ruidoso". Observa los logs de uno o más `source_agents` y, cuando aparece un pattern configurado (p. ej. `FAILED`, `out of memory`), termina exactamente esos source agents — sin tumbar todo el flow. Stopper NO inicia agents posteriores; es puramente una herramienta de apagado controlado. |
| **Cleaner** | El conserje post-mortem. Después de que un Ender o un FlowBacker terminan, el Cleaner elimina los archivos `.log` y `.pid` de los agents a los que estaba conectado, dejando el pool de la sesión como nuevo. Es el único agent que debería conectarse DESPUÉS de Ender. |
| **Sleeper** | Una pausa temporizada. Espera una cantidad de milisegundos configurada, luego inicia todo lo que esté en `target_agents`. Útil para limitar la frecuencia de los loops de polling, darle tiempo a un servicio externo a estabilizarse, o construir ciclos de "cada N segundos" cuando se combina con un Raiser. |
| **Croner** | Un disparador guiado por reloj. Despierta a la `HH:MM` configurada todos los días e inicia sus `target_agents`. Bueno para backups nocturnos, reportes programados, o cualquier flow de "corre esto todos los días a las 3 AM". |

### Agents de enrutamiento

Estos agents deciden A DÓNDE va el flow después, con base en lo que observan en los logs de arriba o en el input del usuario.

| Agent | Descripción |
|-------|-------------|
| **Raiser** | Un lanzador guiado por eventos. Observa continuamente los logs de sus `source_agents` buscando un `pattern` configurado. Cuando aparece el pattern, dispara cada agent en `target_agents`. Raiser es el puente de pan de cada día entre los agents de monitoreo *pasivos* y los agents de acción *activos* — donde quieras "cuando pase X, haz Y", un Raiser es la respuesta correcta. |
| **Forker** | Un router A/B automático. Observa sus source agents buscando dos conjuntos distintos de patterns (`pattern_a` y `pattern_b`); el conjunto que coincida primero determina qué camino toma el flow después (`target_agents_a` o `target_agents_b`). Úsalo cuando una sola señal de arriba pueda significar dos cosas distintas y cada significado tenga su propio chain posterior. |
| **Asker** | Un selector A/B interactivo. Cuando corre, abre un diálogo en la UI del chat que le pide al usuario elegir el Camino A o el Camino B (con leyendas opcionales como "Aprobar" / "Rechazar"). Se lanzan los `target_agents` del camino elegido y el camino rechazado se deja intacto. Tiene un timeout de 5 minutos. Perfecto para aprobaciones con humano en el circuito o experimentos a/b. |
| **Counter** | Un conteo persistente con enrutamiento por umbral. Cada vez que corre incrementa un contador guardado y lo compara contra un `threshold_value`. Si el contador está por debajo del umbral, dispara `target_agents_l` (less); si alcanzó o pasó el umbral, dispara `target_agents_g` (greater). El conteo sobrevive a los reinicios del flow mediante archivos reanim, así que puede manejar loops de "haz esto 5 veces y luego haz aquello". |

### Compuertas lógicas

Estos agents detienen el flow hasta que se cumplen ciertas condiciones de arriba — son primitivas de sincronización puras.

| Agent | Descripción |
|-------|-------------|
| **AND** | Una compuerta AND de dos entradas. Dispara sus `target_agents` sólo cuando AMBOS `source_1` AND `source_2` han producido sus patterns respectivos. La coincidencia queda *enganchada* (latched): una vez que un source coincide, ese lado queda satisfecho hasta que la compuerta dispara. Úsala para exigir que dos caminos paralelos tengan éxito antes de continuar. |
| **OR** | Una compuerta OR de dos entradas. Dispara sus `target_agents` cuando CUALQUIERA de `source_1` OR `source_2` produce su pattern, lo que pase primero. Úsala para patterns de "el primero gana", p. ej. continuar en cuanto termine cualquiera de dos fuentes de datos redundantes. |
| **Barrier** | Una barrera de N entradas (una AND generalizada). Espera hasta que TODOS los `source_agents` configurados hayan iniciado, luego dispara sus `target_agents`. El primer source en llegar se vuelve el watcher que hace el polling; cada llegada posterior deja un archivo de bandera y la compuerta se libera cuando todas las banderas están presentes. Diseñada para la sincronización de tipo fan-in entre muchos caminos paralelos sin condiciones de carrera. |

### Agents de acción

Estos son los agents que *hacen el trabajo real* — corren comandos, consultan APIs, producen archivos, llaman a LLMs, automatizan el escritorio.

| Agent | Descripción |
|-------|-------------|
| **Executer** | Corre un comando de shell arbitrario y dispara sus `target_agents` cuando el comando termina. El stdout y el stderr del comando se capturan en su archivo de log. El agent de "haz algo en esta máquina" más simple y flexible — donde hubieras tecleado un comando en una terminal, un Executer puede hacerlo por ti. **Preferido sobre Keyboarder / Mouser siempre que haya que correr un comando o un paso de build; nunca teclees un comando en una ventana de terminal con Keyboarder — mejor dáselo a Executer.** |
| **Pythonxer** | Corre un script de Python en línea (dado como un string de YAML) detrás de una compuerta ESTRICTA de correctitud: primero parsea el script con `compile()` (un script que no se puede parsear se rechaza, nunca se corre) y luego lo valida con Ruff — cuando `ruff_blocking` es true (el default) cualquier hallazgo de Ruff aborta la ejecución y registra los hallazgos. El script puede usar cualquier paquete instalado. **Los agents posteriores SIEMPRE se disparan después — pase lo que pase (éxito, un rechazo de la compuerta o una falla en ejecución)** — así que Pythonxer nunca deja un flow sin salida; el exit code (0/distinto de cero) sólo maneja el LED y el loop de corrección y reintento de Multi-Turn. Conecta un agent posterior para inspeccionar el resultado/log si un paso sólo debe continuar con éxito. Un flag opcional `execute_forked_window` abre el script en una consola nueva para ver el stdout en vivo. Genial para manipulación de datos ad hoc, lógica a medida, o cualquier cosa para la que escribirías un archivo `.py` de una sola vez. **Preferido sobre Keyboarder / Mouser para ejecutar código y generar contenido calculado; nunca manejes Keyboarder para teclear Python en IDLE o en un editor — mejor dale el código a Pythonxer.** |
| **SQLer** | Ejecuta un bloque de Python contra una instancia de Microsoft SQL Server usando `pyodbc`. El script recibe `cursor` y `conn` como globales inyectados, así que puedes escribir `cursor.execute("SELECT ...")` directamente. Dispara los agents posteriores cuando el SQL termina con éxito. Úsalo para pasos de ETL, verificaciones de esquema, exportaciones de datos, o cualquier cosa que necesite una sesión SQL real. |
| **Mongoxer** | Ejecuta un bloque de Python contra una base de datos MongoDB usando `pymongo`. El script recibe un objeto `db` ya conectado, así que puedes escribir `db.users.find({...})` directamente. Dispara los agents posteriores al tener éxito. El gemelo MongoDB de SQLer — perfecto para lecturas, escrituras y agregaciones sobre document-store dentro de un flow. |
| **Crawler** | Un lector web orientado a desarrolladores con análisis LLM integrado. Trae una URL por HTTP GET y captura **contenido crudo por default** (HTML completo, JS en línea, CSS, headers, JSON-LD, atributos data-*, todo) o texto plano a petición, luego lo envía a un modelo de Ollama con un system prompt centrado en desarrolladores que produce un análisis estructurado. Por **default lee exactamente la página que le das** (`crawl_type: page`); `small-range` recorre los links del mismo sitio de esa página, `medium-range` todos los links, `large-range` recursivamente, cada uno analizando primero la página misma (`include_seed`). Es **a prueba de bloqueos y cuelgues**: cada página tiene un límite duro de reloj (`page_timeout_seconds`, 45 s) y un tope de tamaño, toda la corrida un deadline (`deadline_seconds`, 900 s) y un tope de páginas (`max_pages`, 25). Un muro de bots, un CAPTCHA, un 401/403/429 o un timeout regresan como `status: blocked` / `timeout` y nunca llegan al LLM como contenido de página, y un crawl que no analizó nada termina con una sección que dice NOTHING WAS ANALYZED y por qué. No corre JavaScript: para una página construida por JavaScript usa Playwrighter. Excelente para auditorías de seguridad, análisis de competencia, o cualquier tarea de "dime qué hace realmente esta página". |
| **Googler** | Hace búsqueda web indexada a prueba de bloqueos y cuelgues, luego extrae texto legible/HTML crudo de los mejores resultados o devuelve sólo las URLs encontradas. Toda la corrida obedece UN solo deadline de reloj (`deadline_seconds`, default 120) y cada llamada de red está acotada, así que un motor atascado nunca puede retenerla. El Tier 0 consulta en paralelo seis rutas renderizadas en el servidor por HTTP plano (DuckDuckGo HTML/Lite, Bing, Mojeek, Brave, Yahoo); el Tier 1 abre Chrome real instalado con un perfil persistente (`window_mode` visible/offscreen/headless; con fallback a Chromium incluido) a través de ocho rutas de browser; el Tier 2 responde desde fuentes de conocimiento abierto (Wikipedia, arXiv, OpenAlex, Hacker News, GitHub, Internet Archive, Project Gutenberg) y lo dice. Una guarda de relevancia rechaza respuestas envenenadas (un motor que responde fuera de tema), un clasificador de rechazos nombra los muros de CAPTCHA/anomalía/rate-limit, y un ledger de salud compartido descansa a los motores que rechazan con una escalera de cooldown creciente en vez de machacarlos. `search_status` siempre dice la verdad (ok, no_matches, blocked, unreachable o timeout), nunca un éxito vacío silencioso. Su constructor estructurado de dorks normaliza frases exactas, exclusiones, fechas, rangos, proximidad, filtros de title/URL/text/anchor, operadores de descubrimiento, y grupos entre paréntesis con `OR` en mayúsculas para varios sitios o tipos de archivo. Los presets cubren books, lawful public/open books, papers, manuals, documents, slides, sheets y directory listings; alias como `ebook`, `docs`, `code` y `data` se expanden automáticamente, mientras que los campos explícitos tienen prioridad sobre los defaults del preset. Usa `content_mode: links_only` para cacerías de PDF/EPUB/archivos, luego pasa las URLs a Apirer/File-Extractor/File-Interpreter. Los operadores avanzados de fecha/proximidad/rango son específicos de Google y pueden ampliarse en los motores de fallback; fija `engines: [google]` cuando importe la semántica exacta (una lista explícita se salta el tier de HTTP plano y las fuentes abiertas). El tool directo de Multi-Turn `googler` acepta operadores manuales en `query`, corre este mismo agent como un hijo que se puede matar y que el Cancel del usuario detiene, y reporta un rechazo como `Error: WEB SEARCH BLOCKED` en vez de una respuesta vacía; los campos estructurados son la superficie visual/del pool. Googler sólo encuentra URLs públicas indexadas, nunca resuelve un CAPTCHA por sí mismo (con `captcha_wait_seconds` una persona puede resolver uno en la ventana visible), nunca evade controles de acceso, y deja el copyright, el licenciamiento, la autorización y el uso en manos del operador. |
| **Playwrighter** | Un agent de automatización de browser con scripts e interactivo, construido sobre Playwright (Chromium/Firefox/WebKit). Donde Crawler hace un fetch HTTP estático de un solo tiro y Googler sólo busca, Playwrighter maneja un browser REAL a través de una lista ordenada de pasos — navegar, llenar formularios, hacer clic, presionar teclas, esperar elementos, extraer texto/atributos, screenshot, assert, descargar — así que puede iniciar sesión en un sitio, enviar un formulario de varios pasos, pasar por un wizard, hacer scraping de una single-page-app renderizada con JavaScript detrás de un login, o correr una verificación de UI de extremo a extremo. Pon `headless: false` para verlo manejar, y `hold_open_seconds: N` (alias `hold_open_ms`) para mantener el browser visible N segundos después del último paso antes de que cierre (la perilla de "espera antes de cerrar para que lo pueda ver"); usa `storage_state_in`/`storage_state_out` para llevar una sesión con login iniciado entre corridas. Escribe un bloque `INI_SECTION_PLAYWRIGHTER` (`status`, `assert_result`, valores extraídos) para que un Forker posterior pueda ramificar según pass/fail y Parametrizer pueda pasar los datos extraídos adelante, y siempre dispara `target_agents` (éxito o falla). La contraparte en el canvas visual del tool de Multi-Turn `chat_agent_playwrighter`. |
| **Apirer** | Un agent cliente de API HTTP/REST. Hace una solicitud configurable GET / POST / PUT / DELETE con headers, body y timeout arbitrarios, luego registra el status de la respuesta, el body y la latencia de ida y vuelta en milisegundos. Los headers de autorización se enmascaran en el log por seguridad. Dispara los agents posteriores sin importar el resultado HTTP (así que los reintentos y las ramas de error se conectan después, no dentro del agent). |
| **Kalier** | El bridge de Tlamatini al tooling de seguridad ofensiva de **Kali Linux**, construido sobre el MCP-Kali-Server (https://www.kali.org/tools/mcp-kali-server/). Al dispararse hace POST a la API Flask del MCP-Kali-Server (`server.py`) que corre en una caja Kali y corre UNA capacidad elegida por su campo `action`: `nmap` (escaneo de puertos/servicios), `gobuster` / `dirb` (descubrimiento de contenido y directorios web), `nikto` (escaneo de servidor web), `sqlmap` (prueba de inyección SQL), `wpscan` (escaneo de WordPress), `enum4linux` (enumeración SMB/Samba), `hydra` (fuerza bruta de credenciales), `john` (cracking de hashes), `metasploit` (correr un módulo), `command` (cualquier comando de shell en la caja Kali), o `health` (sondear el servidor de la API y qué herramientas están instaladas). Captura el stdout/stderr de la herramienta en un bloque `INI_SECTION_KALIER` (`action`, `endpoint`, `subject`, `return_code`, `success`, `timed_out`, `server_url`) para que un Forker posterior pueda ramificar según `{success}` / `{return_code}` y Parametrizer pueda pasar el output adelante; SIEMPRE dispara `target_agents` (éxito o falla). Apunta `server_url` al servidor de la API en ejecución (default `http://127.0.0.1:5000`; para una caja Kali remota usa un túnel SSH `ssh -L 5000:localhost:5000 user@KALI_IP`, o ponlo en `http://<KALI_LAN_IP>:5000`). En **chat (Multi-Turn)** nunca repites la URL — Tlamatini es el cliente embebido del MCP-Kali-Server y autoinyecta el **`kali_server_url`** que pusiste una vez en **Config ▸ URLs** como el `server_url` por default en cada corrida de `chat_agent_kalier` (el LLM todavía puede pasar `server_url=` para sobrescribir en una caja de una sola vez); en el canvas pones `server_url` en el diálogo de este nodo. Implementado de forma autocontenida con la stdlib de Python (`urllib`), así que no necesita paquetes extra en el pool de agents. **Sólo para uso autorizado — corre Kalier ÚNICAMENTE contra sistemas que te pertenecen o que tienes autorización explícita de probar (engagement, lab, CTF).** La contraparte en el canvas visual del tool de Multi-Turn `chat_agent_kalier`. |
| **Discoverer** | El bridge de Tlamatini a la suite de herramientas de seguridad **ProjectDiscovery** (https://github.com/projectdiscovery) para recon, mapeo de superficie de ataque y descubrimiento de vulnerabilidades. Al dispararse corre UNA herramienta elegida por su campo `tool`: `subfinder` (enumeración pasiva de subdominios), `httpx` (sonda y fingerprint HTTP), `naabu` (escaneo de puertos), `katana` (crawler/spider), `nuclei` (escaneo de vulnerabilidades por template), o `cvemap` (búsqueda de CVE — corre el `vulnx` de ProjectDiscovery, ya que la API propia de cvemap se retiró en ago 2025; filtra `cvemap_severity`/`cvemap_product`/`cvemap_limit`) — más las meta-acciones `bootstrap` / `validate` / `update_templates` / `list_tools`. Invoca la CLI propia de cada herramienta DIRECTAMENTE (sin MCP server) como Kalier/ESP32er/Arduiner, autocontenido sobre la stdlib de Python. **ZERO-CONFIG**: en la primera llamada descarga un compilador Go PRIVADO en `<install_dir>/Go` y hace `go install` de la herramienta pedida en `<install_dir>/Go/bin-tools` — sin Go del sistema, sin cambiar el PATH (la primera corrida es lenta, luego queda en caché). Captura el stdout de la herramienta + el JSON guardado en un bloque `INI_SECTION_DISCOVERER` (`tool`, `target`, `returncode`, `success`, `findings_count`, `json_path`, `pdcp_used`, `stage`) para que un Forker posterior pueda ramificar según `{success}` / `{findings_count}` y Parametrizer pueda pasar los resultados adelante; SIEMPRE dispara `target_agents` (éxito o falla). La `pdcp_api_key` (ProjectDiscovery Cloud Platform) es OPCIONAL para cada herramienta (levanta el rate limit de cvemap y habilita el upload de AI/nube de nuclei); subfinder lee su propio `provider-config.yaml` para las keys de las fuentes OSINT. Pon la key de PDCP una vez en Config ▸ Access Keys Wizard ▸ 'Security Recon (ProjectDiscovery)' (autoinyectada en cada corrida; redactada de los exports `.flw` y por `regen_secrets.py` antes de un push). `naabu` usa por default un escaneo CONNECT en Windows (sin Npcap/admin); un preflight fail-safe SE NIEGA en vez de escanear mal. **Sólo objetivos autorizados** — subfinder/cvemap son pasivos, pero httpx/naabu/katana/nuclei tocan activamente el objetivo. La contraparte en el canvas visual del tool de Multi-Turn `chat_agent_discoverer`. |
| **Nmapper** | El bridge nmap LOCAL de Tlamatini, **DE SOLO USO**, para pentesters / recon de CTF. ## Notas de mantenimiento

- **Agregar un agent nuevo**: agrega una fila nueva a la tabla relevante de arriba usando el mismo formato de Markdown. El parser sólo requiere `^\|\s*\*\*<Name>\*\*\s*\|\s*<description>\s*\|`. Los encabezados de sección (`### ...`) los ignora el parser; existen puramente para los lectores humanos.
- **Renombrar un agent**: cambia la celda `**Name**` — pero recuerda que la búsqueda se normaliza a alfanumérico en minúsculas, así que `**Kyber-KeyGen**`, `**KyberKeyGen**` y `**kyber keygen**` caen todos en el mismo lugar. Mientras tu normalización coincida con el nombre de display de la DB, el tooltip se queda conectado.
- **Builds congelados**: `build.py` copia este archivo en `dist/manage/agents_descriptions.md` para que termine en el directorio de instalación junto a `Tlamatini.exe`. El cargador de la vista sondea `agents_descriptions.md` primero, luego recurre a `README.md` (así que los despliegues viejos que todavía no se actualizan siguen funcionando).

Selección de modelos: Config → Models administra 38 ajustes de modelo/engine/voz a través de Core, Vision, Speech, Workflows, Documents y Monitoring & messaging para los 21 agents respaldados por modelo. Conserva los `"@config"` entre comillas y los campos registrados omitidos como herencia; nunca los reemplaces con tags adivinados. Los valores literales de canvas/standalone son overrides. El chat envuelto parte de los globales, luego de los argumentos explícitos del tool; el MCP standalone resuelve los valores heredados del template antes de los overrides de la invocación. No ofrezcas argumentos de modelo a menos que el usuario lo pida. Guardar aplica en la siguiente carga de configuración; reconecta el chat y reinicia los agents que ya estén corriendo según haga falta. Talker requiere un modelo compatible con Orpheus y una voz soportada. El engine local/nube de Whisperer y el modelo de cleanup son separados; el cleanup todavía necesita `ollama_cleanup: true`. El audio de video usa su `transcription.model` local independiente. Un modelo de nube de Whisperer vacío selecciona el default del proveedor; un modelo de reparación de LaTeXer vacío desactiva la reparación. Las credenciales, URLs, dispositivos de audio y ajustes de proveedores ACPX/MCP externos siguen siendo separados. Las fallas de modelo de imagen/video se acumulan en el diálogo de error fatal temático compartido. Conserva las tácticas de reintento y recuperación existentes de Tlamatini y las identidades de modelo configuradas. Nunca sustituyas un modelo ni aceptes como éxito un output de observador faltante/de concatenación cruda; un HTTP 410 puede indicar retiro. Robotics no puede reportar PASS a partir de evidencia faltante. Ve `docs/model_configuration.md` para todos los defaults, paths y chequeos de source/frozen.

## Reporte y recuperación de errores de imagen/video (2026-09-26)

Las fallas de modelo de imagen/video se acumulan en un solo diálogo de error fatal compartido, temático y no modal, con una notificación audible. Tlamatini sigue corriendo: conserva su escalera de reintentos/tácticas, los controles de cancelación y las rutas de recuperación de flow configuradas. Conserva las identidades de modelo configuradas; nunca reportes un observador sobreviviente o una concatenación cruda como análisis exitoso. Descartar oculta el diálogo mientras conserva su historial; las fallas nuevas lo reabren. Ve [el contrato de comportamiento y verificación compartido](docs/visual-analysis-errors.md).
