## Workflow Agents

El diseñador visual de workflows trae **86 tipos de agent**, agrupados abajo según su papel dentro de un flow. Arrastra el que quieras al canvas, conéctalos entre sí y presiona *Iniciar*: los agents corren como procesos aparte, cada uno escribiendo su log, y se hablan entre ellos a través de sus archivos `config.yaml`.

### Agents de control

Estos agents le dan forma al ciclo de vida de un flow: cuándo empieza, cuándo termina y qué se limpia al final.

| Agent | Description |
|-------|-------------|
| **Starter** | El punto de entrada de todo flow. Cuando la usuaria hace clic en *Start*, el Starter es el primer agent que corre; su único trabajo es lanzar los agents listados en sus `target_agents`. Piénsalo como el botón verde de "Play" del canvas — no hace ningún trabajo real por sí mismo, simplemente arranca la cadena. |
| **Ender** | Termina un flow de forma ordenada. Mata a todos los agents listados en sus `target_agents`, y luego lanza lo que esté cableado en sus `output_agents` (típicamente un FlowBacker para los respaldos, seguido de Cleaners que borran los archivos transitorios). Usa Ender al fondo de todo flow que deba apagarse por su cuenta. |
| **Stopper** | Un agent quirúrgico de "mata al vecino ruidoso". Vigila los logs de uno o más `source_agents` y, cuando aparece un patrón configurado (p. ej. `FAILED`, `out of memory`), termina exactamente a esos source agents — sin tumbar el flow completo. Stopper NO arranca a los agents que siguen; es puramente una herramienta de apagado controlado. |
| **Cleaner** | El conserje del post-mortem. Después de que un Ender o un FlowBacker termina, el Cleaner borra los archivos `.log` y `.pid` de los agents a los que estaba cableado, dejando el pool de la sesión otra vez en blanco. Es el único agent que debería cablearse DESPUÉS de Ender. |
| **Sleeper** | Una pausa cronometrada. Espera un número configurado de milisegundos y luego arranca todo lo que esté en `target_agents`. Útil para limitar la tasa de los ciclos de sondeo, darle tiempo a un servicio externo para estabilizarse, o construir ciclos de "cada N segundos" cuando se combina con un Raiser. |
| **Croner** | Un disparador manejado por el reloj. Despierta a la `HH:MM` configurada todos los días y arranca sus `target_agents`. Bueno para respaldos nocturnos, reportes programados o cualquier flow de "corre esto todos los días a las 3 de la mañana". Combínalo con Gatewayer si además quieres disparadores por evento dentro del mismo flow. |

### Agents de ruteo

Estos agents deciden HACIA DÓNDE sigue el flow, según lo que ven en los logs de arriba o en lo que responde la usuaria.

| Agent | Description |
|-------|-------------|
| **Raiser** | Un lanzador manejado por eventos. Vigila continuamente los logs de sus `source_agents` buscando un `pattern` configurado. Cuando el patrón aparece, dispara a todos los agents de `target_agents`. Raiser es el puente de pan de cada día entre los agents de monitoreo *pasivos* y los agents de acción *activos* — donde sea que quieras "cuando pase X, haz Y", un Raiser es la respuesta correcta. |
| **Forker** | Un enrutador A/B automático. Observa sus source agents buscando dos conjuntos distintos de patrones (`pattern_a` y `pattern_b`); el conjunto que empate primero determina qué camino toma el flow después (`target_agents_a` o `target_agents_b`). Úsalo siempre que una sola señal de arriba pueda significar dos cosas distintas y cada significado tenga su propia cadena hacia abajo. |
| **Asker** | Un selector interactivo A/B. Cuando se ejecuta, abre un diálogo en la interfaz del chat pidiéndole al usuario que elija la Ruta A o la Ruta B (con leyendas opcionales como "Aprobar" / "Rechazar"). Se lanzan los `target_agents` de la ruta elegida y la ruta rechazada se queda intacta. Tiene un timeout de 5 minutos. Perfecto para aprobaciones con un humano en el circuito o para experimentos a/b. |
| **Counter** | Un conteo persistente con ruteo basado en umbral. Cada vez que se ejecuta incrementa un contador guardado y lo compara contra un `threshold_value`. Si el contador está por debajo del umbral dispara `target_agents_l` (menor); si alcanzó o pasó el umbral dispara `target_agents_g` (mayor). La cuenta sobrevive a los reinicios del flow gracias a los archivos reanim, así que puede manejar ciclos de "haz esto 5 veces y luego aquello". |

### Compuertas lógicas

Estos agents detienen el flow hasta que se cumplen ciertas condiciones más arriba: son primitivas puras de sincronización.

| Agent | Description |
|-------|-------------|
| **AND** | Una compuerta AND de dos entradas. Dispara sus `target_agents` sólo cuando TANTO `source_1` COMO `source_2` han producido sus patrones respectivos. La coincidencia queda *enclavada*: una vez que una fuente coincide, ese lado permanece satisfecho hasta que la compuerta dispara. Úsala para exigir que dos ramas paralelas tengan éxito antes de continuar. |
| **OR** | Una compuerta OR de dos entradas. Dispara sus `target_agents` cuando CUALQUIERA de las dos, `source_1` O `source_2`, produzca su patrón, lo que ocurra primero. Úsala para patrones del tipo "gana el primero", por ejemplo continuar en cuanto termine cualquiera de dos fuentes de datos redundantes. |
| **Barrier** | Una barrera de N entradas (un AND generalizado). Espera hasta que TODOS los `source_agents` configurados hayan arrancado, y entonces dispara sus `target_agents`. El primer source en llegar se vuelve el vigilante que hace el polling; cada llegada posterior deja un archivo bandera y la compuerta se libera cuando todas las banderas están presentes. Diseñada para sincronización de convergencia entre muchas ramas paralelas, sin ninguna condición de carrera. |

### Agents de acción

Estos son los agents que *hacen el trabajo de verdad*: ejecutan comandos, llaman APIs, producen archivos, invocan LLMs y automatizan el escritorio.

| Agent | Description |
|-------|-------------|
| **Executer** | Ejecuta un comando de shell arbitrario y dispara sus `target_agents` cuando el comando termina. El stdout y el stderr del comando se capturan en su archivo de log. El agent de "haz algo en esta máquina" más simple y más flexible — donde sea que hubieras tecleado un comando en una terminal, un Executer puede hacerlo por ti. **Se prefiere sobre Keyboarder / Mouser siempre que haya que correr un comando o un paso de build; nunca teclees un comando en una ventana de terminal a través de Keyboarder — dáselo a Executer en su lugar.** |
| **Pythonxer** | Ejecuta un script de Python en línea (dado como una cadena de YAML) detrás de una compuerta ESTRICTA de correctitud: primero parsea el script con `compile()` (un script que no se puede parsear se rechaza, nunca se corre) y luego lo valida con Ruff — cuando `ruff_blocking` está en true (el valor por defecto) cualquier hallazgo de Ruff aborta la ejecución y los hallazgos quedan registrados en el log. El script puede usar cualquier paquete instalado. **Los agents que siguen SIEMPRE se disparan después — pase lo que pase (éxito, un rechazo de la compuerta o una falla en tiempo de ejecución)** — así que Pythonxer nunca deja un flow sin salida; el exit code (0 / distinto de cero) sólo maneja el LED y el ciclo de arreglar-y-reintentar de Multi-Turn. Conecta un agent más abajo para revisar el resultado/log si un paso sólo debe continuar cuando hubo éxito. Una bandera opcional `execute_forked_window` abre el script en una consola nueva para ver el stdout en vivo. Excelente para manipulación de datos improvisada, lógica a la medida o cualquier cosa para la que escribirías un archivo `.py` de una sola vez. **Se prefiere sobre Keyboarder / Mouser para ejecutar código y generar contenido calculado; nunca manejes Keyboarder para teclear Python dentro de IDLE o de un editor — dale el código a Pythonxer en su lugar.** |
| **Sqler** | Ejecuta un bloque de Python contra una instancia de Microsoft SQL Server usando `pyodbc`. El script recibe `cursor` y `conn` como globales inyectados, así que puedes escribir `cursor.execute("SELECT ...")` directamente. Dispara los agents que siguen cuando el SQL termina con éxito. Úsalo para pasos de ETL, revisiones de esquema, exportaciones de datos, o cualquier cosa que necesite una sesión SQL real. |
| **Mongoxer** | Ejecuta un bloque de Python contra una base de datos MongoDB usando `pymongo`. El script recibe un objeto `db` ya conectado, así que puedes escribir `db.users.find({...})` directamente. Dispara los agents que siguen al tener éxito. El gemelo MongoDB de Sqler — perfecto para lecturas, escrituras y agregaciones sobre almacenes de documentos dentro de un flow. |
| **Crawler** | Un crawler web orientado a desarrolladores, con análisis por LLM integrado. Trae una URL por HTTP GET y captura **el contenido crudo por defecto** (HTML completo, JS inline, CSS, headers, JSON-LD, atributos data-*, todo) o texto plano si se lo pides. Opcionalmente recorre todos los links del mismo dominio o cada link que encuentre. El resultado se manda a un modelo de Ollama con un system prompt centrado en desarrollo que produce un análisis estructurado. Excelente para auditorías de seguridad, análisis de la competencia, o cualquier tarea del tipo "dime qué hace realmente esta página". |
| **Googler** | Hace una búsqueda en Google con la consulta configurada usando un navegador headless real (Playwright), abre las N primeras páginas de resultados, extrae su texto legible y escribe todo en un archivo de salida además de en su log. Donde Crawler ataca una sola URL que ya conoces, Googler es el agent para "encuéntrame lo que haya en la web sobre X" — primero descubre las URLs y después las lee. |
| **Playwrighter** | Un agent de automatización de navegador, guionizado e interactivo, construido sobre Playwright (Chromium/Firefox/WebKit). Donde Crawler hace un fetch HTTP estático de una sola vez y Googler sólo busca, Playwrighter maneja un navegador REAL a través de una lista ordenada de pasos — navegar, llenar formularios, hacer clic, presionar teclas, esperar elementos, extraer texto/atributos, tomar captura de pantalla, hacer assert, descargar — así que puede iniciar sesión en un sitio, enviar un formulario de varios pasos, avanzar por un asistente, raspar una single-page-app renderizada con JavaScript detrás de un login, o correr una verificación de UI de punta a punta. Pon `headless: false` para verlo trabajar, y `hold_open_seconds: N` (alias `hold_open_ms`) para mantener el navegador visible N segundos después del último paso, antes de que cierre (la perilla de "espera antes de cerrar para que yo lo vea"); usa `storage_state_in`/`storage_state_out` para llevar una sesión ya autenticada de una corrida a otra. Escribe un bloque `INI_SECTION_PLAYWRIGHTER` (`status`, `assert_result`, valores extraídos) para que un Forker más abajo pueda ramificar según pasa/falla y Parametrizer pueda pasar los datos raspados hacia adelante, y siempre dispara sus `target_agents` (con éxito o con falla). La contraparte visual en el canvas del tool `chat_agent_playwrighter` de Multi-Turn. |
| **Apirer** | Un agent cliente de API HTTP/REST. Realiza una petición configurable GET / POST / PUT / DELETE con headers, body y timeout arbitrarios, y luego registra en el log el status de la respuesta, el body y la latencia de ida y vuelta en milisegundos. Los headers de Authorization se enmascaran en el log por seguridad. Dispara los agents que siguen sin importar el resultado del HTTP (así los reintentos y las ramas de error se cablean más abajo, no dentro del agent). |
| **Kalier** | El puente de Tlamatini hacia las herramientas de seguridad ofensiva de **Kali Linux**, construido sobre el MCP-Kali-Server (https://www.kali.org/tools/mcp-kali-server/). Al dispararse hace POST a la API Flask del MCP-Kali-Server (`server.py`) que corre en una máquina Kali y ejecuta UNA capacidad seleccionada por su campo `action`: `nmap` (escaneo de puertos/servicios), `gobuster` / `dirb` (búsqueda de contenido y directorios web), `nikto` (escaneo de servidor web), `sqlmap` (pruebas de inyección SQL), `wpscan` (escaneo de WordPress), `enum4linux` (enumeración SMB/Samba), `hydra` (fuerza bruta de credenciales), `john` (cracking de hashes), `metasploit` (correr un módulo), `command` (cualquier comando de shell en la máquina Kali) o `health` (sondea el servidor de la API y qué herramientas están instaladas). Captura el stdout/stderr de la herramienta dentro de un bloque `INI_SECTION_KALIER` (`action`, `endpoint`, `subject`, `return_code`, `success`, `timed_out`, `server_url`) para que un Forker más abajo pueda ramificar según `{success}` / `{return_code}` y Parametrizer pueda canalizar la salida hacia adelante; SIEMPRE dispara sus `target_agents` (éxito o falla). Apunta `server_url` al servidor de la API en ejecución (por defecto `http://127.0.0.1:5000`; para una máquina Kali remota usa un túnel SSH `ssh -L 5000:localhost:5000 user@KALI_IP`, o ponlo en `http://<KALI_LAN_IP>:5000`). En el **chat (Multi-Turn)** nunca repites la URL — Tlamatini es el cliente embebido del MCP-Kali-Server y auto-inyecta el **`kali_server_url`** que configuraste una sola vez en **Config ▸ URLs** como el `server_url` por defecto en cada ejecución de `chat_agent_kalier` (el LLM todavía puede pasar `server_url=` para sobrescribirlo en una máquina puntual); en el canvas configuras `server_url` en el diálogo de este nodo. Está implementado de forma autocontenida con la stdlib de Python (`urllib`), así que no necesita paquetes extra en el pool de agents. **Uso autorizado únicamente — corre Kalier SÓLO contra sistemas que te pertenezcan o que estés explícitamente autorizado a probar (engagement, laboratorio, CTF).** Contraparte visual en el canvas del tool `chat_agent_kalier` de Multi-Turn. |
| **Discoverer** | Puente de Tlamatini hacia la suite de herramientas de seguridad **ProjectDiscovery** (https://github.com/projectdiscovery) para reconocimiento, mapeo de superficie de ataque y descubrimiento de vulnerabilidades. Al dispararse ejecuta UNA herramienta seleccionada por su campo `tool`: `subfinder` (enumeración pasiva de subdominios), `httpx` (sondeo y fingerprint HTTP), `naabu` (escaneo de puertos), `katana` (crawler/araña), `nuclei` (escaneo de vulnerabilidades por plantillas) o `cvemap` (búsqueda de CVE — ejecuta el `vulnx` de ProjectDiscovery, ya que la API propia de cvemap fue retirada en agosto de 2025; filtros `cvemap_severity`/`cvemap_product`/`cvemap_limit`) — además de las acciones meta `bootstrap` / `validate` / `update_templates` / `list_tools`. Invoca el CLI propio de cada herramienta DIRECTAMENTE (sin server MCP) igual que Kalier/ESP32er/Arduiner, autocontenido sobre la biblioteca estándar de Python. **SIN CONFIGURACIÓN**: en la primera llamada descarga un compilador de Go PRIVADO dentro de `<install_dir>/Go` y hace `go install` de la herramienta pedida en `<install_dir>/Go/bin-tools` — sin Go del sistema, sin cambiar el PATH (la primera ejecución es lenta, después queda en caché). Captura el stdout de la herramienta + el JSON guardado en un bloque `INI_SECTION_DISCOVERER` (`tool`, `target`, `returncode`, `success`, `findings_count`, `json_path`, `pdcp_used`, `stage`) para que un Forker más abajo pueda ramificar según `{success}` / `{findings_count}` y Parametrizer pueda pasar los resultados adelante; SIEMPRE dispara sus `target_agents` (éxito o fallo). La `pdcp_api_key` (ProjectDiscovery Cloud Platform) es OPCIONAL para todas las herramientas (levanta el límite de tasa de cvemap y habilita la subida a la nube / IA de nuclei); subfinder lee su propio `provider-config.yaml` para las llaves de fuentes OSINT. Configura la llave PDCP una sola vez en Config ▸ Access Keys Wizard ▸ 'Security Recon (ProjectDiscovery)' (se auto-inyecta en cada ejecución; se redacta de los exports `.flw` y por `regen_secrets.py` antes de un push). `naabu` usa por defecto un escaneo CONNECT en Windows (no necesita Npcap ni permisos de administrador); un preflight a prueba de fallos SE NIEGA en vez de escanear mal. **SÓLO OBJETIVOS AUTORIZADOS** — subfinder/cvemap son pasivos, pero httpx/naabu/katana/nuclei tocan activamente el objetivo. Contraparte visual en el canvas del tool `chat_agent_discoverer` de Multi-Turn. |
| **Nmapper** | El puente LOCAL de Tlamatini hacia nmap, **SÓLO DE USO**, para pentesters / recon de CTF. Ejecuta un `nmap` real que la usuaria instaló por su cuenta — **NUNCA incluye ni redistribuye nmap** (la NPSL de nmap prohíbe integrarlo en un producto sin una licencia OEM de paga), así que un escaneo siempre usa un nmap que la usuaria ya tiene (resuelto desde el PATH → `C:\Program Files\Nmap\nmap.exe` → una copia en `%LOCALAPPDATA%\Tlamatini\nmap`). Si no encuentra ninguno SE NIEGA de forma elegante con instrucciones de instalación, y `action='install'` (o `auto_install`) descarga y lanza el instalador OFICIAL y GRATUITO de nmap desde nmap.org — la descarga y la instalación con permisos de administrador las hace la usuaria, y eso además trae Npcap. Elige UNA capacidad con `action`: `quick` (`-sT -sV -sC -Pn -T4 --top-ports 1000`, el arranque para CTF) / `full` (los 65535 puertos TCP) / `top_ports` / `version` / `scripts` (NSE dirigido) / `host_discovery` / `udp` / `custom` (base segura + `custom_args` validados; se rechazan los metacaracteres del shell) / `validate` / `install`. Parsea el XML de `-oX` de nmap y conserva el reporte de `-oN`, y emite un bloque `INI_SECTION_NMAPPER` (`action`, `target`, `scan_technique`, `ports`, `return_code`, `success`, `hosts_up`, `open_ports`, `npcap_present`, `xml_path`, `output_path`, `stage`) para que un Forker más abajo pueda ramificar según `{success}` / `{open_ports}`; SIEMPRE dispara sus `target_agents`. Es el hermano de CLI directo de Kalier/Discoverer, autocontenido sobre la librería estándar de Python. **Distinto de Kalier** (una caja Kali REMOTA vía MCP-Kali-Server) y de **Discoverer** (la suite de ProjectDiscovery): Nmapper es el nmap LOCAL instantáneo y sin instalación. **SÓLO OBJETIVOS AUTORIZADOS** — escanea únicamente hosts que te pertenecen o que tienes autorización explícita para probar (por ejemplo scanme.nmap.org). Contraparte visual en el canvas del tool `chat_agent_nmapper` de Multi-Turn. |
| **Unrealer** | Maneja una instancia del editor de Unreal Engine 5 a través del protocolo TCP del plugin Unreal MCP (por defecto 127.0.0.1:55557 — el plugin ya debe estar corriendo dentro de UE5; el agent no arranca el motor). | **Blenderer** | Maneja una instancia de Blender a través del socket TCP del add-on OFICIAL de Blender MCP (por defecto localhost:9876 — el add-on ya debe estar corriendo dentro de Blender con "Online access" habilitado y el server iniciado; el agent no lanza Blender). A diferencia del protocolo de despacho por verbos de Unreal, el formato de cable de Blender MCP es un protocolo de EJECUCIÓN DE CÓDIGO — cada corrida envía `{"type":"execute","code":<python>,"strict_json":<bool>}` (enmarcado con NUL) y Blender ejecuta ese Python (que asigna un dict `result`) — así que Blenderer expone un CATÁLOGO RICO DE ACCIONES seleccionado por su campo `command`, en lugar de obligarte a escribir Python a mano para cada tarea: de PASO DIRECTO `execute_code` (ejecuta Python `bpy` arbitrario — la escotilla de escape universal); de SÓLO LECTURA `ping` / `scene_info` / `get_objects` / `get_object_detail` / `blendfile_summary`; y de MUTACIÓN/SALIDA `create_object` (cube/sphere/cylinder/cone/plane/monkey/torus), `delete_object`, `set_material` (color base Principled), `screenshot` y `render` (las salidas a archivo van por defecto bajo el directorio Temp de Tlamatini). Implementado de forma autocontenida con la biblioteca estándar de Python (socket crudo enmarcado con bytes NUL), así que el pool de agents no necesita paquetes extra. | **Talker** | TEXT-TO-SPEECH (TTS): HABLA el texto en voz alta a través de un dispositivo de salida de audio del sistema (bocinas), manejando una conexión OLLAMA que corre un modelo neuronal de TTS (por defecto `Orpheus-3b-FT`) — el hermano de síntesis de voz de la familia de media (AudioPlayer reproduce un ARCHIVO ya existente; Talker GENERA habla a partir de texto). Pon en `input_text` las palabras a pronunciar. **SÓLO VOZ FEMENINA (Tlamatini es mujer): una voz masculina está PROHIBIDA POR DISEÑO, sin excepción.** `voice` elige una de las voces FEMENINAS permitidas de Orpheus: tara [por defecto], leah, jess, mia, zoe (`gender` sólo acepta `female`, y se usa cuando `voice` está vacío). Pedir una voz masculina (leo/dan/zac) o `gender: male` hace que Talker cierre por completo su ejecución y reporte "male voice is forbidden by design — NOW CLOSING.. BYE" — nunca sustituye y nunca suena masculino. `emotion` teje una etiqueta paralingüística dentro del habla (laugh/chuckle/sigh/cough/sniffle/groan/yawn/gasp) — o escribe `<laugh>` etc. directamente dentro de `input_text`. `language` le pasa una pista al modelo (el modelo base es sólo inglés; un fine-tune multilingüe habla otros idiomas). `model`/`ollama_url`/`ollama_token` configuran la conexión con Ollama; las perillas de generación son `temperature`, `top_p`, `top_k`, `min_p`, `repetition_penalty` (mantenlo ≥ 1.1), `max_tokens`, `seed`. El modelo transmite TOKENS de audio que el códec neuronal SNAC decodifica a una forma de onda de 24 kHz; el WAV se guarda en `output_dir` (por defecto la carpeta Música del usuario, bajo `TlamatiniTalker`) y se reproduce en las bocinas (`device_index`/`device_name`/`volume_percent`/`sample_rate`; con `play_audio: false` se guarda sin reproducir). Emite un bloque `INI_SECTION_TALKER` (`output_path`, `output_dir`, `filename`, `model`, `language`, `voice`, `gender`, `emotion`, `sample_rate`, `audio_seconds`, `char_count`, `played`, `status`) para que un Parametrizer/Forker más abajo pueda leer la ruta del WAV hablado y ramificar según `{status}`; SIEMPRE dispara sus `target_agents` (éxito o falla). Es observacional/de salida (no cambia ningún estado persistente), así que no aparece en el Exec Report. **NOTA**: obtener los tokens sólo necesita la stdlib, pero renderizar audio audible necesita `snac` + `torch` (un vocoder neuronal) instalados (`pip install snac torch`); sin ellos Talker guarda los tokens de audio y reporta `status: tokens_only`. Contraparte visual en el canvas del tool `chat_agent_talker` de Multi-Turn. |
| **Mouser** | Control programático del mouse vía PyAutoGUI. O mueve el puntero de forma aleatoria durante un tiempo (comportamiento anti-inactividad) o hacia una coordenada específica de la pantalla (modo "localizado"); en modo localizado también puede emitir un clic configurado una vez alcanzado el destino (ninguno / izquierdo / derecho / medio / doble-izquierdo / doble-derecho / doble-medio). Úsalo para manejar UIs de escritorio desde un flow cuando no hay API disponible. **Reservado para automatización genuina de UI de escritorio pedida explícitamente por la usuaria (demos de mouse / puntero / clic, movimiento anti-inactividad, replay de GUI). Nunca uses Mouser como parte de un flow de escritura de código — File-Creator escribe el archivo, Executer / Pythonxer lo ejecuta; ninguno de esos necesita eventos de puntero.** |
| **Windower** | El administrador de ventanas del trío de UI de escritorio (Windower = la ventana misma, Mouser = los clics dentro de ella, Keyboarder = escribir en ella). Localiza la ventana de una aplicación por su título y ejecuta UNA operación de ciclo de vida sobre ella — `focus`/traer al frente, `minimize`, `maximize`, `restore`, `move`, `resize`, `move_resize`, `close`, `topmost`/`untopmost`, o `arrange` (acomodar/mosaico en una región de la pantalla) — o `list`a todas las ventanas abiertas con su posición, tamaño y estado. El emparejamiento es por `substring` (por defecto), `exact` o `regex`, con `match_index` para elegir entre ventanas del mismo título. Implementado de forma autocontenida con la API Win32 (pywin32), incluyendo la transferencia confiable de foco entre procesos (AttachThreadInput) portada del Windows-MCP de Microsoft. Emite un bloque `INI_SECTION_WINDOWER` (`action`, `window_title`, `matched`, `match_count`, `state`, `left`, `top`, `width`, `height`) para que un Forker más abajo pueda ramificar según `{matched}`/`{state}` y Parametrizer pueda pasar la geometría adelante; siempre dispara sus `target_agents`. **Usa Windower — no Mouser — siempre que la meta sea la ventana como un todo (traerla al frente, acomodarla, redimensionarla, cerrarla por título); Mouser sólo hace clic en controles dentro de una ventana.** Contraparte visual en el canvas del tool `chat_agent_windower` de Multi-Turn. |
| **Keyboarder** | Control programático del teclado vía PyAutoGUI. Envía una secuencia de pulsaciones que mezcla texto literal (entre comillas simples o dobles), nombres de teclas sueltos (p. ej. `enter`, `tab`, `f5`) y combinaciones unidas con `+` (p. ej. `ctrl+s`, `ctrl+shift+t`), con un retardo configurable entre pulsaciones. Combínalo con Mouser y Shoter para automatizar cualquier app con interfaz gráfica que no tenga una interfaz de scripting. **Reservado para automatización genuina del teclado pedida explícitamente por la usuaria (demos de tecleo en el Bloc de notas, inyección de atajos en apps de terceros, repeticiones de GUI). Nunca uses Keyboarder para escribir código fuente, scripts, configuraciones ni el contenido de ningún archivo — usa File-Creator (escribe el archivo de forma atómica), Pythonxer (ejecuta Python en línea) o Executer (ejecuta un comando de shell / de build) en su lugar.** |

### Agents de notificación

Estos son agents *terminales*: reaccionan a lo que pasa más arriba pero NO arrancan nada después. Su trabajo es avisarle al mundo de afuera que algo ocurrió.

| Agent | Description |
|-------|-------------|
| **Notifier** | El agent de notificaciones en el navegador. Vigila sus `source_agents` buscando cualquiera de una lista de `search_strings` separada por comas y, al haber coincidencia, deja caer un archivo `notification.json` que la UI de chat de Tlamatini consulta y renderiza como un popup del DOM dentro del navegador (con sonido opcional). Los offsets de archivo por fuente y los archivos reanim hacen que nunca vuelva a procesar contenido viejo del log, ni siquiera después de reiniciar. |
| **Emailer** | Envía un correo por SMTP cuando se le dispara. Remitente, contraseña, lista de destinatarios, asunto y cuerpo configurables. Patrón común: conecta un Raiser para detectar el éxito o la falla de un pipeline río arriba y haz que dispare a Emailer para notificar a una lista de correo del equipo. |
| **RecMailer** | Un receptor de correo por IMAP con análisis por LLM. Sondea un buzón configurado, descarga los mensajes nuevos y le pregunta a un modelo de Ollama si el cuerpo coincide con alguna de tus `keywords_or_phrases`. Registra en el log cada coincidencia con la `outcome_word` configurada. Úsalo para que un flow reaccione a la llegada de un correo real, p. ej. una alerta de un SaaS externo. |
| **Whatsapper** | El único agent de envío/recepción de WhatsApp, construido SÓLO sobre la **WhatsApp Cloud API oficial** de Meta (Graph API). Tres `mode`s: `send` (publica un `message`/`template`, luego arranca sus `target_agents` y muere), `receive` (escucha en el webhook oficial durante `rx_max_seconds`, luego arranca sus `target_agents` y muere) y auto (lo infiere de la configuración). Dirígete al destinatario por un `contact_name` resuelto desde la libreta de Contactos (`contacts.json`, junto a `config.json`) o por un número literal en `whatsapp.to`. Las credenciales (`whatsapp.phone_number_id` / `whatsapp.access_token` / `whatsapp.graph_base` / `whatsapp.api_version`) se siembran una sola vez desde los globales de config.json, así que los prompts del chat nunca las repiten. Según la política de WhatsApp, un `message` de formato libre sólo se entrega dentro de la ventana de 24 horas — para escribirle a alguien EN FRÍO, pasa un `template` aprobado (con `template_language` / `template_params`). Elige QUÉ NÚMERO envía con `provider`: `cloud` (por defecto) envía desde el número DE NEGOCIO vía la Cloud API oficial (aplican las reglas de templates / System User / ventana de 24h); `web` envía desde TU PROPIO número personal automatizando WhatsApp Web tras un login por código QR de una sola vez (sin templates, sin System User). Funciona con lenguaje natural, así que "mándalo como yo" / "desde mi propio WhatsApp" → `provider=web` y "como el negocio" / "oficial" → `provider=cloud`. La ruta `web` es NO OFICIAL (maneja WhatsApp Web) y puede lograr que Meta banee un número; el bloque de configuración `web:` (`headless` / `login_wait_seconds` / `settle_seconds` / `profile_dir`) la ajusta y el login por QR se recuerda por instalación. ARRANCA sus `target_agents` y es fuente de Parametrizer emitiendo `INI_SECTION_WHATSAPPER` (campos `mode`, `direction`, `recipient`, `status`, `message_id`; cuerpo = `response_body`). Muy útil como canal de "avísame al celular cuando se rompa el build" o como disparador entrante manejado por webhook. |
| **Telegrammer** | El único agent de envío/recepción de Telegram que usa exclusivamente superficies oficiales de Telegram. El modo bot usa la **Bot API** oficial de Telegram (`telegram.bot_token` de @BotFather); el modo de usuario, opcional, usa la sesión oficial de la API de Telegram (`telegram.api_id`, `telegram.api_hash`, `telegram.session_name`/`session_string`) para que los envíos privados a un `@username` puedan quedarse legibles para un humano dentro de los configs. Tiene tres `mode`s: `send` (publica un `message` a un `telegram.chat_id`/`@username` o a un `contact_name`, luego arranca sus `target_agents` y muere), `receive` (escucha durante `rx_max_seconds`, opcionalmente filtrando por `rx_from_chat_id` / `rx_match`, luego arranca sus `target_agents` y muere) y auto (lo infiere del config). Puedes dirigirte al destinatario con un `contact_name` resuelto desde `contacts.json`; ese contacto puede conservar `telegram: "@username"`. Telegrammer usa un caché local de usernames más la búsqueda oficial `getChat`/`getUpdates` de la Bot API, y cae de vuelta a la API oficial de sesión de usuario cuando está configurada. Elige QUÉ IDENTIDAD envía con `provider`: `bot` envía COMO el bot (Bot API), `user` envía COMO tu propia cuenta con sesión iniciada (sesión de usuario, para envíos privados a un `@username`); el lenguaje natural funciona, así que "mándalo como yo" → `provider=user` y "como el bot" → `provider=bot`, mientras que `auto` (el predeterminado) usa tu cuenta para los `@usernames`/`+teléfono` privados y el bot para los ids numéricos y los canales. ARRANCA sus `target_agents` y emite `INI_SECTION_TELEGRAMMER` (campos `mode`, `direction`, `chat_id`, `status`, `message_id`; el body es `response_body`). |
| **Zavuerer** | El puente de Tlamatini hacia **Zavu** (https://www.zavu.dev) — UNA sola API unificada para SMS, WhatsApp, Telegram, Email y Voz. En lugar de cablear por separado Twilio (SMS) + la WhatsApp Cloud API de Meta + SMTP, Zavuerer envía a través del único endpoint REST de Zavu con una sola API key, con ruteo inteligente por ML opcional (`channel: auto`) y fallback automático de canal (por ejemplo, si WhatsApp falla → SMS). Al dispararse ejecuta UNA capacidad seleccionada por su campo `action`: `send` (hace POST de un mensaje — `to` con un teléfono en +E.164 para SMS/WhatsApp/Voz/Telegram o una dirección de correo para Email, `text`, `channel` ∈ `auto`/`sms`/`whatsapp`/`telegram`/`voice`/`email`, y opcionalmente `subject`/`from_sender`/`fallback`) o `health` (sondea la API y si la key está configurada). Captura el resultado dentro de un bloque `INI_SECTION_ZAVUERER` (`action`, `channel`, `to`, `status`, `message_id`, `success`, `base_url`; el cuerpo es `response_body`) para que un Forker más abajo pueda ramificar según `{success}` / `{status}` y Parametrizer pueda canalizar el id del mensaje hacia adelante; SIEMPRE dispara sus `target_agents` (éxito o falla). La `zavu_api_key` se configura una sola vez (consigue la key en https://www.zavu.dev — registrarse es gratis, pero Zavu cobra por mensaje enviado, con pago sobre la marcha) — si está vacía, un `send` se REHÚSA con un mensaje de una línea que dice "set your Zavu key" (status `refused`) en vez de fallar en silencio. Está implementado de forma autocontenida con la stdlib de Python (`urllib`), así que no necesita ningún SDK en el pool de agents. **Sólo destinatarios autorizados y que hayan dado su consentimiento — respeta las reglas anti-spam / de consentimiento de cada canal (A2P, la ventana de 24 horas de WhatsApp, GDPR).** Contraparte visual en el canvas del tool `chat_agent_zavuerer` de Multi-Turn. |
| **Monitor-Log** | Un vigilante puro de archivos de log con detección de eventos por LLM. Sondea un `logfile_path` configurado, alimenta las líneas nuevas a un modelo de Ollama, y escribe en el log `outcome_word` (por defecto `TARGET_FOUND`) cuando detecta una coincidencia. Está diseñado para ser el `source_agents` aguas arriba de un Raiser — juntos forman el mini-flow canónico de "reaccionar a una línea de log". |
| **Monitor Netstat** | La versión de puertos de red de Monitor-Log. Sondea las conexiones TCP/UDP abiertas del sistema, se las pasa al LLM y emite `TARGET_FOUND` cuando la condición de red configurada coincide. Úsalo para "avísame si se abre el puerto X" o "dispara si no hay conexión al host Y durante N segundos". |
| **FlowHypervisor** | El watchdog propio del flow. Un agent administrado por el sistema que observa el log de cada uno de los demás agents en un intervalo de sondeo configurable, le pregunta a un modelo de Ollama si el flow como conjunto está sano, y escribe `OK` o `ATTENTION NEEDED { explanation }` en su propio log. La UI del chat lee esas entradas y expone los problemas como alertas ATTENTION!. Se detiene automáticamente cuando no hay otros agents corriendo, y se auto-detiene después de 3 ciclos inactivos como red de seguridad. |

### Agents de utilería

Agents de pegamento e infraestructura: no producen output directamente, pero hacen que el resto del canvas sea más fácil de conectar.

| Agent | Description |
|-------|-------------|
| **Parametrizer** | El motor de interconexión. Lee la salida estructurada de un "source agent" río arriba (cualquiera de los 46 agents de salida estructurada que emiten un bloque `INI_SECTION_<TYPE>` — p. ej. Apirer, Crawler, Summarizer, Googler, ACPXer, Discoverer, Kalier, Telegrammer, Whatsapper, Zavuerer) y escribe los campos seleccionados dentro del `config.yaml` de un "target agent" río abajo mediante un esquema visual de interconexión. Cuando existen varios elementos de salida (p. ej. Crawler devuelve 5 URLs), itera: llena la configuración, arranca el target, espera, repite. El agent que convierte un canvas estático en un verdadero pipeline de datos. |
| **FlowBacker** | Una utilidad de respaldo pasiva. Cuando se dispara (típicamente por Ender), copia todo el directorio del pool de la sesión desplegada hacia un `target_directory` configurado, sobrescribiendo cualquier respaldo previo de la misma sesión, y luego lanza sus `target_agents` (los Cleaners). El paso de "guarda antes de borrar" en cualquier flow que termine con limpieza. |
| **FlowCreator** | El diseñador de flows con IA. Lee `agentic_skill.md` (la biblioteca de patrones canónicos de flow de Tlamatini) y le pide a un modelo de Ollama que genere un JSON completo de workflow `.flw` a partir de una descripción en lenguaje natural. Úsalo para arrancar un flow sin arrastrar y cablear a mano: describe lo que quieres y FlowCreator emite un flow que después puedes refinar en el canvas. TAMBIÉN se puede llamar directamente desde el chat mediante el tool envuelto `chat_agent_flowcreator` — dile "crea un flow que haga X" y escribe en disco un archivo `.flw` real y cargable en el canvas (por defecto en la carpeta Temp de la aplicación) para que lo abras en el Panel de Control. |
| **Gatewayer** | El gateway de entrada. Un agent de larga duración que escucha eventos externos, ya sea en un webhook HTTP (por defecto `127.0.0.1:8787`) o en un watcher de carpeta (folder-drop), normaliza cada evento en un envelope canónico, lo persiste en disco y despacha en serie a los agents que siguen. Soporta autenticación por bearer-token, HMAC y lista blanca de IPs, además de deduplicación, persistencia y recuperación ante caídas. Es el agent que permite que el mundo exterior *llame hacia adentro* de un flow — webhooks, pushes de IoT, callbacks de SaaS, descargas batch programadas, todos son bienvenidos. |
| **Gateway Relayer** | Un relay determinista y sin LLM que traduce formatos de webhook de terceros (por ejemplo el `X-Hub-Signature-256` de GitHub) al esquema HMAC de `timestamp + body` que espera Gatewayer. Valida la firma del proveedor de origen, transforma el payload, lo firma para Gatewayer y lo reenvía. Úsalo cuando quieras que un flow reciba webhooks nativos de GitHub / GitLab / Stripe / Shopify sin tener que parchar Gatewayer. |
| **NodeManager** | Un registro de infraestructura de larga duración. Mantiene un inventario vivo de nodos locales y remotos, sondea la salud de cada uno (ping, TCP, SSH, WinRM, HTTP), clasifica el estado (`ONLINE` / `OFFLINE` / `DEGRADED` / `UNKNOWN`), detecta cambios de capacidades, persiste el estado entre reinicios, exporta manifiestos filtrados a demanda y dispara sus `target_agents` ante los eventos de nodo configurados. Es el agent torre de control para flotas de máquinas. |

### Agents de criptografía

Primitivas de criptografía post-cuántica, deterministas y de vida corta.

| Agent | Description |
|-------|-------------|
| **Kyber-KeyGen** | Genera un par de llaves pública/privada CRYSTALS-Kyber post-cuánticas en base64. Soporta tres variantes: `kyber-512`, `kyber-768` (la predeterminada) y `kyber-1024`. La salida se registra en un bloque estructurado para que un Parametrizer más abajo pueda enrutar las llaves directamente hacia Kyber-Cipher y Kyber-DeCipher. |
| **Kyber-Cipher** | Cifra un buffer de texto plano con una llave pública de CRYSTALS-Kyber. Internamente usa **encapsulación** Kyber para derivar un secreto compartido y AES-256-CTR para cifrar el buffer; el agent registra en el log la encapsulación, el IV y el texto cifrado en base64, todo cableado para que Parametrizer pueda canalizarlos hacia Kyber-DeCipher. |
| **Kyber-DeCipher** | El inverso de Kyber-Cipher. Descifra un texto cifrado en base64 usando la **llave privada** CRYSTALS-Kyber correspondiente más la encapsulación y el IV que emitió Kyber-Cipher. Emite el texto plano recuperado en su log, listo para File-Creator u otro consumidor. |
